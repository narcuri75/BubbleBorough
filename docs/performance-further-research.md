# Further performance research for Bubble Borough

Reviewed October 3, 2026. This is a research report; the game's runtime and build files were not changed. It follows the [first five implemented improvements](performance-first-five-implementation.md), which already cover profiler accuracy, production HTTP compression/revalidation, decoration routing, indexed fish lookups, and shared swim geometry. Those are excluded from the recommendations below.

The order estimates the likelihood of disturbing existing features, based on how much code shares the result, how difficult invalidation is, and whether a change touches rendering, interaction timing, or persistent player state. These are qualitative engineering judgments, not measured probabilities. Benefit and feature risk are separate: the smallest changes rank first even when their likely savings are small. Within the same risk band, the order is approximate.

Browser frame-time, GPU, and allocation traces were not captured in this review. Source-confirmed repetition is identified below; expected speedups remain hypotheses until measured on representative devices.

| Order | Improvement | Estimated feature risk | Expected benefit | Features to verify |
| --- | --- | --- | --- | --- |
| 1 | Remove the duplicate glass clear; reuse the reduced-motion media query | Very low | Small reduction in per-frame API calls and allocation | Glass overlays; live preference changes |
| 2 | Write editor control content only when its value changes | Low | Less DOM work while editing | Labels, affordability, residents, accessibility |
| 3 | Share the caustic mask's base inverse transform | Low | Less matrix allocation/calculation in decorated scenes | Camera transforms; lighting mask alignment |
| 4 | Bound shadow query row ranges and index receiver registration | Low to moderate | Less work as support artwork and decoration count grow | Placement surfaces, flips, ordering, shadows |
| 5 | Reuse stable WebGL turn setup and vertex layouts | Low to moderate | Fewer API calls during turn bursts | Body/fin switches; debug settings; context recovery |
| 6 | Refresh editor tray geometry when layout actually changes | Moderate | Less geometry/style work while editing | Camera framing, reflow, scrolling, pointer alignment |
| 7 | Generate a conservative minified production bundle | Moderate | Reduced download and parse input; primarily startup | Globals, debug hooks, script order, deployment |
| 8 | Prepare active-scene masks and turn shapes before first visible use | Moderate | Fewer first-turn and scene-switch hitches | Startup time, custom artwork, marker data |
| 9 | Bound turn resources and reuse scratch surfaces of matching dimensions | Moderate | Steadier memory; fewer backing-surface resizes | In-flight turns, eviction, changing image sizes |
| 10 | Prioritize immediately needed assets over unused startup variants | Moderate | Earlier complete interactive scene; lower decode peaks | Immediate feeding, cleaning, purchases, image recovery |
| 11 | Cache safe static scene segments and cull fully invisible draw work | Moderate to high | Lower repeated drawing cost | Depth/cave order, effects outside sprite bounds, camera |
| 12 | Move isolated pixel preprocessing to a worker | Moderate to high | Reduced main-thread preprocessing stalls | Custom imports, cancellation, ownership, fallback |
| 13 | Migrate measured save stalls to asynchronous persistence | High | Fewer large-save interruptions | Save durability, migration, recovery, action ordering |
| 14 | Batch fish drawing on the GPU; consider a worker renderer afterward | High | Potentially large dense-scene improvement | Artwork parity, transparency, cave passes, latency |
| 15 | Offer lower visual quality; alter simulation cadence only separately | Highest; intentional feature tradeoffs | Predictable reduction in visual or simulation workload | Visual fidelity, movement, collision, behavior timing |

1. **Remove a duplicate clear and retain the media-query object.** In [renderTank](../game/public/app-src/rendering/tank-and-water.js), the virtual glass surface is cleared before `clearStageDisplaySurfaces()` clears the full physical glass surface. Both occur before the scene's glass drawing. Confirm no intervening helper draws to glass, then retain the full-surface clear alone. In [updateStageRenderView](../game/public/app-src/assets/custom-content.js), `matchMedia("(prefers-reduced-motion: reduce)")` is called every processed frame. Retain one query and read its live `matches` property, or maintain a boolean through its change event. These are small cleanups, unlikely to resolve a major bottleneck by themselves. [Media-query change events](https://developer.mozilla.org/en-US/docs/Web/API/MediaQueryList/change_event) allow preference changes to remain live.

2. **Separate editor content changes from animated positioning.** The animation loop calls [updateSelectedDecorActionButtons](../game/public/app-src/decor/layout-and-layers.js) on every processed frame. With a selected decoration, it repeatedly assigns text, titles, datasets, disabled state, and ARIA labels. Compare actual existing values before assignments; continue updating positions when the camera or selection moves. Reading the existing values first avoids introducing a broad stale-content cache. Coins, group membership, residence assignments, depth, and selection must still appear immediately. Browser guidance recommends limiting DOM/layout work and grouping geometry reads before writes; the source reads here do not establish that forced reflow occurs. [Layout guidance](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing).

3. **Reuse the base caustic transform, preserving the live local transform.** [setLightweightCausticMaskTransform](../game/public/app-src/rendering/tank-and-water.js) constructs and inverts the same stage matrix for every marked image. Compute that inverse once for the current scale/offset triple, or once per render. Continue reading and multiplying each source context's current transform: flipped and locally transformed decorations need it. Preserve the existing DOMMatrix operations initially instead of substituting different floating-point arithmetic. An executed fixture confirmed 100 base inversions for 100 marks. It did not measure matrix CPU time. [getTransform](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getTransform) returns a separate matrix object, so caching the base must not imply caching the changing source transform.

4. **Reduce shadow query and registration work without a persistent world-geometry cache.** [getDecorSurfaceMarkedYAtWorldX](../game/public/app-src/decor/hit-testing.js) visits every mask row, rejecting rows outside the requested vertical interval. Bound the loop conservatively to the candidate interval and retain the exact existing comparisons, alpha threshold, traversal direction, and closest-point calculation. A research-only prototype reduced five queries against a 1,024-row mask from 5,120 row visits to 60; alpha reads remained 50. It matched the original result in 2,000 seeded fixtures covering different scales, positions, transparency, and both flips. This establishes sample numerical parity, not complete game parity or an FPS gain.

   Separately, [registerDecorShadowSurface](../game/public/app-src/rendering/decor.js) uses `findIndex` as it rebuilds the receiver array each render. A fixture of 100 unique receivers made 4,950 ID comparisons. A per-frame ID-to-position map can preserve the array and replacement order without that scan. Preserve the reverse-order receiver choice in `drawCasterShadowOnDecorSurfaces`. Follow-on column/run metadata for `getDecorSurfacePlaneYAtWorldX` is possible but needs additional mask-lifetime, flip, and tie-break validation. Keep RGB surface data available: black marked pixels are valid support surfaces.

5. **Reuse stable turn-renderer setup.** [renderFishTurnV26VolumeCanvas](../game/public/app-src/rendering/fish-turn-v26.js) repeats blend/depth setup, vertex attribute configuration, and many constant uniform uploads per turn render. Initialize stable state on renderer creation and use vertex array objects where supported, retaining the current fallback. Keep pose, fin settings, aspect, turn phase, and mutable debug values live; reset cached assumptions when programs or contexts change. Do not reorder transparent body/fin passes. [WebGL guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) supports stable vertex layouts and avoiding unnecessary state work. The present shader, quality, blending, and draw order can remain intact.

6. **Make tray geometry updates event driven.** [updateStageRenderView and isStageEditTrayActuallyVisible](../game/public/app-src/assets/custom-content.js) check computed style and element rectangles during editing. Use ResizeObserver for size changes plus explicit open/close, reflow, scroll, transform, and viewport invalidation. Observe movement as well as size: ResizeObserver alone cannot cover every position change. Retain camera easing on each animation frame using the current cached target. This has more risk than value-comparing control labels because stale geometry can break tool alignment. [ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver) reports size changes; confirm fewer layout/style costs in a browser trace before considering the change successful.

7. **Minify a separate production artifact conservatively.** [build-app-bundle.cjs](../scripts/build-app-bundle.cjs) assembles shared-scope fragments into the canonical bundle and checks function inventories. Keep that development artifact and its checks intact. Start a separate production output without property mangling, unsafe transforms, or unproven changes to global function names; generate source maps and exercise the deployed output. HTTP compression is already implemented for the production Node route. Minification and later optional-feature splitting address additional startup work, not an established steady-FPS bottleneck. Arbitrary fragments cannot be lazy-loaded safely until shared dependencies are made explicit. [JavaScript payload and splitting guidance](https://web.dev/articles/reduce-javascript-payloads-with-code-splitting).

8. **Prepare exactly the active scene's expensive data.** [getImageAlphaMask](../game/public/app-src/assets/image-storage-and-import.js) performs pixel readback/copy on misses, and [turn shape preprocessing](../game/public/app-src/rendering/fish-turn-v26.js) computes shape data on first use. Warm those outputs in bounded work after relevant artwork is ready, before their first visible use. Immutable catalog art can use build-generated, content-versioned sidecars with the same algorithm. Preserve full RGBA/marker contracts and original resolution. Avoid preparing the entire catalog; warm-up can increase startup time and memory. Existing image loaders already set asynchronous decoding, so adding that flag again offers no new improvement. An explicit [decode promise](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode) may help readiness coordination where appropriate, but does not guarantee that every later draw or upload is free of stalls.

9. **Give remaining resources a bounded lifetime.** The turn renderer's shape, texture, and buffer maps retain entries until renderer disposal; existing disposal uses `deleteTexture` and `deleteBuffer`, but regular per-entry budgets are absent. Pin artwork used by active turns and retire unused entries at safe transitions or in bounded maintenance. Cover CPU shapes and derived artwork as well as GPU handles. Avoid repeated eviction/reupload when an active scene exceeds a budget. Separately, [surface shadow scratch rendering](../game/public/app-src/rendering/decor.js) and the shared turn canvas change backing dimensions when consecutive objects differ in size. Prototype a small pool keyed by exact dimensions; it preserves current sampling more directly than scaling everything into one larger canvas. Use byte limits and test alternating sizes and repeated tank cycling. [WebGL resource guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) supports explicit lifetime management. More retained surfaces are a cost, so neither pooling nor eviction is automatically faster.

10. **Reduce the startup readiness set carefully.** [Startup](../game/public/app-src/ui/tool-modes-and-debug-panels.js) already loads the active tank and lazy-loads store artwork, but still awaits all gravel catalogs, machinery variants, cursors, and food/medicine artwork. [preloadImages](../game/public/app-src/assets/image-storage-and-import.js) launches its deduplicated list through one Promise.all. Separate visible and immediately usable artwork from optional variants; test a bounded loading/decoding queue for the optional group. Keep current content settings, retry/late-load recovery, and instant tool use. Loading fewer variants helps startup and memory, while over-restricting concurrency can slow startup. Choose concurrency from measurements, not a universal magic number.

11. **Cache and cull only when the complete rendered result permits it.** Background composition, water shading, and suitable static floor segments still draw every render, although gravel/depth caches already exist. Start with one bounded static composition surface; keep animated water lines, plants, caustics, and moving shadows live. Invalidate for camera, size/DPR, waterline, lighting, background, substrate, and asset readiness. Separately, early-reject fully invisible draw work only using bounds that include glow, shadow, deformation, and portal exterior replays. Keep simulation and animation state advancing even when no pixels are visible. Canvas already clips pixels; application culling is useful only if it avoids measurable preparation/submission work. Preserve the two cave-back passes and their sandwich order. [Canvas optimization guidance](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas) supports static pre-rendering and layers. More compositor surfaces or large blits can offset savings.

12. **Use a worker for isolated image processing first.** Mask extraction, distance-field preparation, and custom-image transforms are narrower candidates than moving the whole game loop. Transfer buffers or bitmaps with explicit ownership and a scene generation; discard stale results when players switch tanks or replace artwork. Preserve cancellation, loading errors, and a main-thread fallback. Workers shift CPU work and introduce message/transfer overhead; copying a large scene each frame can create a new bottleneck. [Worker guidance](https://web.dev/articles/off-main-thread) and [OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas) describe the available mechanisms. Browser support must be checked for each operation used, not inferred from the existence of Worker alone.

13. **Change persistence only after measuring a save hitch.** Deferred saves already coalesce work, but [saveState](../game/public/app-src/tank/events-recaps-and-save.js) still serializes and writes localStorage synchronously. Measure housekeeping, snapshot/copy, JSON serialization, and storage independently. If those stalls matter, use versioned IndexedDB transactions, ordered save generations, and last-committed recovery; acknowledge a save after its transaction completes. Preserve current import/export, desktop persistence, cloud synchronization, purchase timing, and error behavior. Test quota failures, interrupted writes, rapid actions, reload, and tab closure. Do not rely on an asynchronous unload write. [Web Storage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) confirms that localStorage is synchronous and identifies IndexedDB as an asynchronous alternative. Persistence errors have a larger consequence than a visual mismatch, which raises this item's risk rank.

14. **Prototype GPU batching before changing rendering architecture.** Shared swim geometry reduces calculations but still submits one Canvas draw per slice. Batch the current strip quads while retaining exact sample rectangles, overlap, alpha, ordering, and phase. A narrow optional path with the existing renderer as fallback is safer than replacing every renderer at once. Compare dense swimming and simultaneous-turn scenes on real weaker GPUs. The current turn canvas is immediately consumed by Canvas 2D; do not casually remove `preserveDrawingBuffer` or `flush`. A full worker renderer would also require explicit state/input messages and coordination with main-thread overlays; it shifts work without inherently reducing GPU fill cost. [WebGL batching guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices), [OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas).

15. **Treat quality and simulation reductions as explicit tradeoffs.** The game already caps ordinary idle animation at 30 FPS, shop animation at 24 FPS, and normal DPR at 1.25; it also adjusts swim strips and turn layers under load. Further optional changes could reduce only decorative particles, blur, shadow quality, or render resolution. These intentionally change appearance. Reducing fish AI, collision, or simulation cadence has broader consequences for schooling, feeding, cave traversal, movement, and action response. Keep that as a separate, last-resort design decision with time-based behavior validation. Do not apply blanket integer snapping to smoothly moving fish merely because generic canvas advice suggests integer coordinates.

Before implementation, record comparable baseline scenes for ordinary play, dense support decor, cave traversal, feeding, simultaneous turns, editing, tank switching, and large saves. Record device/browser, viewport/DPR, population, effects, and the active frame cap. Compare processed-frame p50/p95/p99 work, visual output, allocation/GC, and long-session memory; measure startup separately. The existing profiler correction enables useful measurements but does not replace a browser trace. [Chrome runtime profiling](https://developer.chrome.com/docs/devtools/performance) and [allocation profiling](https://developer.chrome.com/docs/devtools/memory-problems/allocation-profiler) provide complementary evidence. CPU throttling cannot reproduce a real mobile GPU.

The strongest next implementation candidate is **item 4**, following a baseline trace: it has directly demonstrated wasted operations and a narrowly scoped prototype. Items 1-3 are smaller safe cleanups. Items 5-6 should follow when traces show turn-setup or editor-layout costs. Later items depend on the bottleneck that remains.

The reproducible source audit is in `.review-artifacts/performance-further/source-audit.cjs`; run `node .review-artifacts/performance-further/source-audit.cjs`. It uses extracted functions with stubbed dependencies and a research-only bounded-loop prototype. No game functions were patched, no full regression suite was rerun, and no measured FPS improvement is claimed.
